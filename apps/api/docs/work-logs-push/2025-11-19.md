## 📋 작업 개요

## 🔄 푸시 전송 흐름

### 1. 단일 유저 전송 흐름

```
1. API 요청: POST /push/notifications/send-to-user
   ↓
2. PushNotificationService.sendToUser(userId, message)
   ↓
3. Prisma: 활성화된 푸시 토큰 조회 (isActive = true)
   ↓
4. FcmProvider.sendToMultiple(tokens, message)
   ↓
5. Firebase Cloud Messaging API 호출
   ↓
6. processResults(): 결과 처리
   ├─ savePushLog(): PushNotificationLog 테이블에 저장
   ├─ PushToken 상태 업데이트 (successCount/failureCount)
   └─ invalidateToken(): 실패한 토큰 비활성화
   ↓
7. 응답 반환: { success, sentCount, failureCount }
```

### 2. 전체 유저 전송 흐름

```
1. API 요청: POST /push/notifications/send-to-all
   ↓
2. PushNotificationService.sendToAll(message, filter)
   ↓
3. Prisma: 조건에 맞는 모든 푸시 토큰 조회
   - isActive = true
   - marketingEnabled = true (옵션)
   ↓
4. FcmProvider.sendToMultiple(tokens, message)
   - 500개씩 자동 분할 처리
   ↓
5. Firebase Cloud Messaging API 호출 (배치)
   ↓
6. processResults(): 각 토큰별 결과 처리
   ↓
7. 응답 반환
```

## 🔑 핵심 헬퍼 함수

### processResults()
푸시 전송 결과를 처리하는 공통 함수
- 로그 저장 (`savePushLog`)
- 실패한 토큰 비활성화 (`invalidateToken`)

```typescript
private async processResults(
  pushTokens: any[],
  results: PushSendResult[],
  message: PushMessage,
  type: PushNotificationType,
) {
  for (let i = 0; i < results.length; i++) {
    const result = results[i];
    const pushToken = pushTokens[i];

    // 1. 푸시 전송 로그 저장
    await this.savePushLog(pushToken, result, message, type);

    // 2. 실패한 토큰 비활성화
    if (this.shouldInvalidateToken(result)) {
      await this.invalidateToken(pushToken, result.errorCode);
    }
  }
}
```

### savePushLog()
푸시 전송 로그를 데이터베이스에 저장
- PushNotificationLog 테이블에 기록
- PushToken 테이블의 통계 필드 업데이트 (successCount, failureCount, lastUsedAt)

### shouldInvalidateToken()
토큰 비활성화 여부 판단
- FCM 에러 코드가 `invalid-registration-token` 또는 `registration-token-not-registered`인 경우 비활성화

### invalidateToken()
토큰을 비활성화하고 이유를 기록
- `isActive = false`
- `invalidatedAt` 저장
- `invalidReason` 저장

## 🔍 기술적 의사결정

### 1. YAGNI 원칙 적용
**질문**: "캠페인 테이블이 있는데, 지금 사용해야 하나요?"
**답변**: 아니오. YAGNI(You Aren't Gonna Need It) 원칙에 따라 필요할 때 구현합니다.
- 현재는 로그만 남기고, 캠페인 관리는 실제로 필요할 때 추가

### 2. 타입 설계: type vs data.subType
- `type` (Enum): 대분류 - 통계 및 분석용
- `data.subType` (String): 세부 타입 - 비즈니스 로직용
- 이유: 통계 쿼리 성능 vs 유연성 트레이드오프

### 3. 헬퍼 함수 추출
**질문**: "반복되는 코드를 어떻게 정리할까?"
**답변**: 공통 함수로 추출
- `processResults()`: 결과 처리 공통화
- `savePushLog()`: 로그 저장 공통화
- `shouldInvalidateToken()`: 토큰 무효화 판단 로직
- `invalidateToken()`: 토큰 무효화 처리

### 4. Storage vs Store 분리
**질문**: "saveAuthData()에서 setUser()까지 한 번에 처리하면 안 될까?"
**답변**: 아니오. 레이어 책임 분리를 위해 분리 유지
- Storage: 순수 데이터 저장 레이어 (AsyncStorage)
- Store: UI 상태 관리 레이어 (Zustand)
- 결합도 낮추고 순환 의존성 방지
