### 1. 파일 관리 구조 설계 문제 발견 및 해결

#### 문제점
- `file_uploads` 테이블과 `content_files` 테이블이 각각 파일 정보를 중복 관리
- 파일 마스터 테이블 없이 관계 테이블이 파일 정보를 직접 보유하는 비정규화 구조
- 중앙 집중식 파일 관리 불가능

#### 해결 방안
**Files 마스터 테이블 생성 + 관계 테이블 분리**

```
변경 전:
FileUpload (file_uploads)
├─ originalName, filename, mimetype, size, path (파일 정보 직접 보유)
└─ userId (관계 정보)

ContentFile (content_files)
├─ fileUrl, fileName, fileSize, mimeType (파일 정보 직접 보유)
└─ contentId (관계 정보)

변경 후:
File (files) - 마스터
├─ originalName, storedName, filePath, fileSize, mimeType
└─ storageType, isActive, createdAt, updatedAt

UserFile (user_files) - 관계 테이블
├─ userId, fileId (관계 정보)
└─ fileType, uploadCategory, uploadedAt (메타데이터)

ContentFile (content_files) - 관계 테이블
├─ contentId, fileId (관계 정보)
└─ sortOrder, createdAt (메타데이터)
```

### 3. Prisma Schema 업데이트

#### 변경된 모델

**File 모델 (신규 생성)**
```prisma
model File {
  id            Int           @id @default(autoincrement())
  originalName  String        @map("original_name")
  storedName    String        @unique @map("stored_name")
  filePath      String        @map("file_path")
  fileSize      Int           @map("file_size")
  mimeType      String        @map("mime_type")
  storageType   String        @default("local") @map("storage_type")
  isActive      Boolean       @default(true) @map("is_active")
  createdAt     DateTime      @default(now()) @map("created_at")
  updatedAt     DateTime?     @updatedAt @map("updated_at")
  userFiles     UserFile[]
  contentFiles  ContentFile[]

  @@map("files")
}
```

**UserFile 모델 (FileUpload에서 변경)**
```prisma
model UserFile {
  id              Int              @id @default(autoincrement())
  userId          Int              @map("user_id")
  fileId          Int              @map("file_id")
  uploadedAt      DateTime         @map("uploaded_at")
  fileType        String           @map("file_type")
  uploadCategory  String           @map("upload_category")
  user            User             @relation(fields: [userId], references: [id])
  file            File             @relation(fields: [fileId], references: [id], onDelete: Cascade)
  missionAttempts MissionAttempt[]

  @@map("user_files")
}
```

**ContentFile 모델 (리팩토링)**
```prisma
model ContentFile {
  id        Int      @id @default(autoincrement())
  contentId Int      @map("content_id")
  fileId    Int      @map("file_id")
  sortOrder Int      @default(0) @map("sort_order")
  createdAt DateTime @map("created_at")
  content   Content  @relation(fields: [contentId])
  file      File     @relation(fields: [fileId])

  @@map("content_files")
}
```

## 🎓 배운 점

### 데이터베이스 설계 원칙
1. **마스터 테이블은 종속성을 가지면 안 된다**
   - 나쁜 예: Quiz 테이블에 missionId, contentId 직접 포함

   - 마스터 데이터는 마스터 테이블에서 조인으로 가져와야 함
   - 관계 메타데이터만 관계 테이블에 저장

3. **중복 제거의 중요성**
   - uploaded_by는 UserFile 관계로 충분 (Files에 불필요)
   - 파일 정보는 Files 한 곳에서만 관리

### 2. 인증 가드 추가

#### 비즈니스 정책
- **목록은 모두에게 노출** (마케팅 용도)
- **칼럼 상세**: 로그인만 하면 무료 시청
- **강의 상세**: 구독자 또는 활성 챌린지 참여자만 시청 가능

#### 적용한 가드

| API | 가드 | 설명 |
|-----|------|------|
| `GET /api/contents/lectures` | `@UseGuards(JwtAuthGuard)` | 강의 목록 조회 |
| `GET /api/contents/columns` | `@UseGuards(JwtAuthGuard)` | 칼럼 목록 (페이지네이션 + 정렬) |
| `GET /api/contents/columns/today` | `@UseGuards(JwtAuthGuard)` | 오늘의 칼럼 5개 |
| `GET /api/contents/:id` (칼럼) | `@UseGuards(JwtAuthGuard)` | 칼럼 상세 조회 |
| `GET /api/contents/:id` (강의) | JWT + **구독자/챌린저 체크** | 강의 동영상 시청 |

#### 강의 접근 제어 로직
```typescript
// content.controller.ts - getContentDetail()
if (content.type === 'LECTURE') {
  const user = await prisma.user.findUnique({
    where: { id: userId },
    select: {
      subscriptionStatus: true,
      userChallenges: {
        where: { status: 'ACTIVE' },
        select: { id: true }
      }
    }
  });

  // 구독자(NEWCOMER 아닌 경우) OR 활성 챌린지 참여자
  const isSubscriber = user.subscriptionStatus !== UserSubscriptionStatus.NEWCOMER;
  const hasActiveChallenge = user.userChallenges.length > 0;

  if (!isSubscriber && !hasActiveChallenge) {
    throw new ForbiddenException('강의는 구독자 또는 활성 챌린지 참여자만 이용할 수 있습니다');
  }
}
```

## 🔗 칼럼 이전글/다음글 네비게이션 추가

### 요구사항
칼럼 상세보기에서 이전글/다음글 이동 버튼 제공

### 구현
**content.service.ts - getContentById() 수정**

```typescript
// 칼럼인 경우 이전글/다음글 추가
if (content.type === 'COLUMN') {
  // 이전글 (현재 글보다 ID가 작은 것 중 가장 큰 ID)
  const prevContent = await this.prisma.content.findFirst({
    where: {
      type: 'COLUMN',
      isActive: true,
      id: { lt: id }
    },
    orderBy: { id: 'desc' },
    select: { id: true, title: true }
  });

  // 다음글 (현재 글보다 ID가 큰 것 중 가장 작은 ID)
  const nextContent = await this.prisma.content.findFirst({
    where: {
      type: 'COLUMN',
      isActive: true,
      id: { gt: id }
    },
    orderBy: { id: 'asc' },
    select: { id: true, title: true }
  });

  return {
    ...content,
    prevContent: prevContent || null,
    nextContent: nextContent || null
  };
}
```

### 응답 구조
```json
{
  "id": 26,
  "title": "현재 칼럼 제목",
  "content": "...",
  "type": "COLUMN",
  "prevContent": {
    "id": 25,
    "title": "이전 칼럼 제목"
  },
  "nextContent": {
    "id": 27,
    "title": "다음 칼럼 제목"
  }
}
```

### 동작 방식
- **정렬 기준**: ID 순서 (등록 순서)
- **이전글**: ID < 현재ID 중 가장 큰 ID
- **다음글**: ID > 현재ID 중 가장 작은 ID
- **첫 번째 글**: prevContent = null
- **마지막 글**: nextContent = null
- **칼럼만 적용**: 강의 등 다른 타입은 미적용

### 2. 최종 설문 API 구조 (4개)

#### API 1: 설문 질문 조회
**엔드포인트**: `GET /api/surveys/:challengeSurveyId/questions`

**사용 방법:**
1. `GET /api/challenges/my-active` 호출
2. 응답의 `surveys[].id` 값 추출
3. 해당 id를 challengeSurveyId로 사용

**응답 데이터:**
- 질문 목록 (20개)
- 각 질문마다 5개 옵션 포함 (id, text, score)
- 카테고리 순서: 염증 → 대사밸런스 → 장건강 → 면역과민반응

---

#### API 2: 설문 제출
**엔드포인트**: `POST /api/surveys/:challengeSurveyId/complete`

**Request Body:**
```json
{
  "type": "BEFORE",
  "answers": [
    { "questionId": 1, "optionId": 3 },
    { "questionId": 2, "optionId": 4 },
    ...
  ]
}
```

**동작:**
- 모든 질문(20개)에 답변 필수
- 같은 type으로 재제출 시 기존 답변 덮어쓰기
- 카테고리별 점수 집계 및 동물 캐릭터 추천

---

#### API 3: 사전/사후 설문 비교
**엔드포인트**: `GET /api/surveys/:challengeSurveyId/comparison`

**사용 시점:**
- BEFORE, AFTER 설문 모두 완료한 후
- 21일차 완료 후 결과 화면

**응답 데이터:**
- 카테고리별 사전/사후 점수 비교
- 총점 변화
- 추천 동물 캐릭터 (사전/사후)

**주의사항:**
- 사전 또는 사후 미완료 시 해당 데이터 null 반환

---

#### API 4: 내 설문 결과 조회
**엔드포인트**: `GET /api/surveys/results/me?type=BEFORE`

**사용 시점:**
- 마이페이지에서 설문 이력 조회
- 과거 작성한 설문 결과 확인
- 특정 시점(BEFORE/AFTER) 결과만 필요할 때

**쿼리 파라미터:**
- `type=BEFORE`: 사전 설문만 조회
- `type=AFTER`: 사후 설문만 조회
- 미지정: 전체 조회

**응답 데이터:**
- 설문 결과 ID
- 설문 타입 (BEFORE/AFTER)
- 카테고리별 점수
- 총점
- 추천 동물 캐릭터
- 작성일시

### 5. 설문 시스템 주요 버그 수정

#### 버그 1: field name 오류
```
Unknown field `text` for select statement on model `SurveyOption`
```
- **원인**: Prisma 스키마는 `optionText`인데 `text`로 조회
- **해결**: `optionText` 조회 후 `text`로 매핑

#### 버그 2: Challenge day 계산 오류
```
currentDay = 3 (실제는 2일차여야 함)
```
- **원인**: 로컬 타임존 메서드 사용 (`getDate()`)
- **해결**: UTC 메서드로 변경 (`getUTCDate()`)

#### 버그 3: API 파라미터 불일치
- **문제**: Frontend는 `challengeSurveyId`만 있는데 API는 `surveyId` 요구
- **해결**: 모든 API를 `challengeSurveyId` 기반으로 통일

#### 설문 플로우
