## 📋 작업 1: Rate Limiting 구현

### 문제 상황
- 푸시 API에 아무런 Rate Limit이 없어 **무분별한 발송 가능**

```typescript
async getPushLogs(query: PushLogQueryDto): Promise<PushLogListResponseDto> {
  const { page = 1, limit = 100, userId, success, type } = query;
  
  // 필터 조건 구성
  const where: any = {};
  if (userId !== undefined) where.userId = userId;
  if (success !== undefined) where.success = success;
  if (type) where.type = type;

    where, skip: (page - 1) * limit, take: limit, orderBy: { sentAt: 'desc' },
  });
  
  return { logs, total, page, limit, totalPages };
}
```

## 📋 작업 3: 토큰 중복 검증 강화

### 문제 상황

현재 PushToken 테이블의 Unique 제약:
```prisma
@@unique([userId, deviceId, provider])
```

**문제 시나리오**:
1. 유저가 디바이스 X에서 앱 설치 → FCM 토큰 `TOKEN123` 발급
2. `userId=1, deviceId=X, token=TOKEN123` 저장
3. 유저가 앱 삭제 후 재설치 → FCM이 **같은 토큰** `TOKEN123` 재사용
4. 클라이언트가 실수로 `deviceId=Y`로 전송
5. **결과**: 동일한 토큰이 두 개의 deviceId에 중복 저장 → **푸시 2번 발송**

### 구현 내용

**파일**: `src/push/services/push-token.service.ts` **(38-68번 줄)**

```typescript
async registerToken(userId: number, dto: RegisterPushTokenDto) {
  const { token, deviceId, platform } = dto;

  // 1. 동일한 토큰이 다른 deviceId에 등록되어 있는지 확인 (38-48번 줄)
  const existingTokenWithSameValue = await this.prisma.pushToken.findFirst({
    where: {
      token,
      provider: 'FCM',
      isActive: true,
      NOT: { deviceId: deviceId || token },
    },
  });

  // 2. 중복 발견 시 기존 토큰 비활성화 (50-68번 줄)
  if (existingTokenWithSameValue) {
    this.logger.warn(`⚠️ 동일 토큰이 다른 디바이스에 존재`);
    
    await this.prisma.pushToken.update({
      where: { id: existingTokenWithSameValue.id },
      data: {
        isActive: false,
        invalidatedAt: new Date(),
        invalidReason: 'TOKEN_REASSIGNED_TO_NEW_DEVICE',
      },
    });
  }

  // 3. 새로운 토큰 등록 (70-97번 줄, 기존 upsert 로직)
  const pushToken = await this.prisma.pushToken.upsert({ ... });
  return this.mapToResponseDto(pushToken);
}
```

### 동작 흐름 예시

**현재 DB**: `id=1, userId=10, deviceId=X, token=TOKEN123, isActive=true`

**새 요청**: `{ token: "TOKEN123", deviceId: "Y" }`

**검증 실행**: 같은 TOKEN123을 가진, 하지만 deviceId가 Y가 아닌 토큰 찾기 → id=1 발견

**기존 토큰 비활성화**: `UPDATE push_tokens SET isActive=false, invalidReason='TOKEN_REASSIGNED_TO_NEW_DEVICE' WHERE id=1`

**새 토큰 등록**: `id=2, userId=10, deviceId=Y, token=TOKEN123, isActive=true`

**최종 DB 상태**:
```
id=1, deviceId=X, token=TOKEN123, isActive=false  ← 비활성화
id=2, deviceId=Y, token=TOKEN123, isActive=true   ← 새로 등록
```

### 효과
- ✅ 중복 푸시 완전 차단
- ✅ 데이터 정합성 향상
- ✅ `invalidReason`으로 추적 가능

## 📋 작업 4: Topic 기반 푸시 인프라 세팅

### 배경: FCM Topic이란?

**일반 방식**: 유저 1000명에게 발송 → 1000개 토큰 조회 → FCM 1000번 호출

**Topic 방식**: "marketing" 토픽 구독자에게 1번만 발송 → FCM이 알아서 배포

**활용 예시**:
- `all-users`: 전체 공지사항
- `marketing`: 마케팅 동의 유저
- `event-123`: 특정 이벤트 참여자
- `inactive-7days`: 7일간 미접속 유저

```typescript
@Injectable()
export class PushTopicService {
  // Topic 구독 (30-63번 줄)
  async subscribeTopic(userId: number, dto: SubscribeTopicDto) {
    const tokens = dto.tokens || await this.getUserActiveTokens(userId);
    const success = await this.fcmProvider.subscribeToTopic(tokens, dto.topic);
    return { success, message: `${dto.topic} 토픽에 구독되었습니다` };
  }

  // Topic 구독 해제 (72-103번 줄)
  async unsubscribeTopic(userId: number, dto: UnsubscribeTopicDto) {
    const tokens = dto.tokens || await this.getUserActiveTokens(userId);
    const success = await this.fcmProvider.unsubscribeFromTopic(tokens, dto.topic);
    return { success, message: '구독이 해제되었습니다' };
  }

  // Topic으로 푸시 전송 (112-136번 줄)
  async sendToTopic(dto: SendPushToTopicDto) {
    const result = await this.fcmProvider.sendToTopic(dto.topic, { ... });
    return { success: result.success, messageId: result.messageId };
  }

  // 유저의 활성 토큰 조회 (145-161번 줄)
  private async getUserActiveTokens(userId: number): Promise<string[]> {
    const pushTokens = await this.prisma.pushToken.findMany({
      where: { userId, isActive: true, provider: 'FCM' },
    });
    return pushTokens.map((pt) => pt.token);
  }
}
```

## 🎯 핵심 인사이트

### 1. Rate Limiting은 필수
- 특히 금전적 비용이 드는 API는 **반드시 보호 필요**
- 전체 발송은 1시간/1번으로 **가장 엄격하게 제한**

### 2. 로그는 운영의 생명줄
- 로그 조회 API는 **기능 개발과 동시에** 만들어야 함
- 페이지네이션은 **처음부터** 넣어야 나중에 고생 안 함

### 3. 데이터 정합성은 서비스 레벨에서 보장
- DB 제약만으로는 **복잡한 비즈니스 로직 처리 불가**
- 감사 추적을 위해 **삭제보다 비활성화**가 나음

### 4. 인프라는 미리 준비
- Topic 같은 인프라는 **사용 전에 미리 세팅**
- 지금 시간 투자가 **나중에 시간 절약**

### 5-1. PushNotificationType enum 일원화

**문제 상황**:

```typescript
async updatePushLogStatus(
  userId: number,
  logId: number,
  status: 'READ' | 'CLICKED',
) {
  // 1. 로그 조회 및 권한 확인
  const log = await this.prisma.pushNotificationLog.findFirst({
    where: { id: logId, userId },
  });

  if (!log) {
    return { success: false, message: '푸시 알림을 찾을 수 없습니다' };
  }

  // 2. 상태에 따라 업데이트
  const updateData: any = {};
  if (status === 'READ' && !log.readAt) {
    updateData.readAt = new Date();
  } else if (status === 'CLICKED' && !log.clickedAt) {
    updateData.clickedAt = new Date();
    // CLICKED는 READ를 포함하므로 readAt도 함께 설정
    if (!log.readAt) {
      updateData.readAt = new Date();
    }
  }

  // 이미 업데이트된 경우 중복 처리 방지
  if (Object.keys(updateData).length === 0) {
    return { success: true, message: '이미 처리된 상태입니다' };
  }

  // 3. 업데이트 실행
  await this.prisma.pushNotificationLog.update({
    where: { id: logId },
    data: updateData,
  });

  return { success: true, message: '푸시 상태가 업데이트되었습니다' };
}
```

**주요 로직**:
- userId 권한 검증 (다른 유저의 로그 수정 불가)
- CLICKED 시 readAt도 자동 설정
- 중복 업데이트 방지 (idempotent)

## 📋 작업 7: 푸시 알림 스케줄링 시스템 구현

### 작업 배경
운영팀의 효율성 향상을 위한 **자동화된 푸시 발송 시스템** 구축:
- 반복 발송: 매일 아침 리마인더, 매주 이벤트 알림 등
- 예약 발송: 특정 시간에 자동 발송되는 마케팅 캠페인
- 배치 처리: 1분마다 자동 실행되는 스케줄러

### 요구사항
1. **ONCE (단발성)**: 특정 시간에 1회만 발송
2. **RECURRING (반복)**: Cron 표현식으로 주기적 발송
3. **스케줄 관리**: 생성, 수정, 삭제, 활성화/비활성화
4. **실행 추적**: 스케줄별 실행 통계 (성공/실패 횟수)
5. **캠페인 로그**: 각 실행에 대한 이력 관리
6. **관리자 UI**: 스케줄 관리 및 모니터링 화면

```typescript
async executeScheduledCampaign(schedule: any) {
  // 1. campaignKey 생성 (중복 실행 방지)
  const campaignKey = `schedule-${schedule.id}-${Date.now()}`;

  // 2. 중복 체크 (unique constraint)
  const existing = await this.prisma.pushNotificationCampaign.findUnique({
    where: { campaignKey }
  });
  if (existing) {
    return { success: false, message: '이미 실행 중인 캠페인입니다' };
  }

  // 3. 타겟 유저 조회
  const targetUsers = await this.queryTargetUsers(schedule.targetQuery);

  // 4. 캠페인 생성 (PENDING)
  const campaign = await this.prisma.pushNotificationCampaign.create({
    data: {
      scheduleId: schedule.id,
      campaignKey,
      campaignType: schedule.scheduleType === 'ONCE' ? 'SCHEDULED' : 'RECURRING',
      title: schedule.title,
      body: schedule.bodyTemplate,
      type: schedule.type,
      category: schedule.category,
      status: 'PENDING',
      targetCount: targetUsers.length,
    }
  });

  // 5. PROCESSING 상태로 변경
  await this.prisma.pushNotificationCampaign.update({
    where: { id: campaign.id },
    data: { status: 'PROCESSING', startedAt: getNowKST() }
  });

  // 6. 실제 푸시 전송
  let sentCount = 0;
  let failCount = 0;
  for (const user of targetUsers) {
    try {
      await this.pushNotificationService.sendToUser(user.id, {
        title: schedule.title,
        body: schedule.bodyTemplate,
        imageUrl: schedule.imageUrl,
        data: schedule.data,
      });
      sentCount++;
    } catch (error) {
      failCount++;
    }
  }

  // 7. COMPLETED 상태로 변경
  await this.prisma.pushNotificationCampaign.update({
    where: { id: campaign.id },
    data: {
      status: sentCount > 0 ? 'COMPLETED' : 'FAILED',
      sentCount,
      failCount,
      completedAt: getNowKST()
    }
  });

  // 8. ONCE 타입이면 자동 비활성화
  if (schedule.scheduleType === 'ONCE') {
    await this.prisma.pushNotificationSchedule.update({
      where: { id: schedule.id },
      data: { isActive: false }
    });
  }

  // 9. 스케줄 통계 업데이트
  await this.prisma.pushNotificationSchedule.update({
    where: { id: schedule.id },
    data: {
      lastExecutedAt: getNowKST(),
      totalExecutions: { increment: 1 },
      successfulExecutions: { increment: sentCount > 0 ? 1 : 0 },
      failedExecutions: { increment: sentCount === 0 ? 1 : 0 }
    }
  });

  return {
    success: true,
    campaignId: campaign.id,
    sentCount,
    failCount
  };
}
```

**설계 포인트**:
- campaignKey로 중복 실행 방지 (DB unique constraint)
- ONCE 타입은 실행 후 자동 비활성화
- 스케줄 통계 자동 업데이트
- Campaign 상태 흐름: PENDING → PROCESSING → COMPLETED/FAILED

```typescript
@Injectable()
export class PushSchedulerService {
  private readonly logger = new Logger(PushSchedulerService.name);

  constructor(
    private readonly pushScheduleService: PushScheduleService,
    private readonly pushCampaignService: PushCampaignService,
  ) {}

  /**
   * 매분 실행되는 크론잡
   * Cron: '0 * * * * *' = 매분 0초에 실행
   * Timezone: Asia/Seoul (KST)
   */
  @Cron('0 * * * * *', {
    name: 'check-push-schedules',
    timeZone: 'Asia/Seoul',
  })
  async handleScheduledPushes() {
    this.logger.log('🕐 [PushScheduler] 스케줄 확인 시작');

    try {
      // 1. 실행 가능한 스케줄 조회
      const schedules = await this.pushScheduleService.getExecutableSchedules();

      if (schedules.length === 0) {
        this.logger.log('ℹ️ [PushScheduler] 실행할 스케줄 없음');
        return;
      }

      this.logger.log(`📋 [PushScheduler] 실행할 스케줄: ${schedules.length}개`);

      // 2. 각 스케줄별로 캠페인 실행
      for (const schedule of schedules) {
        try {
          // ONCE 타입: 예약 시간 재확인
          if (schedule.scheduleType === 'ONCE') {
            const scheduledTime = new Date(schedule.oneTimeScheduledAt);
            const now = new Date();
            if (scheduledTime > now) {
              continue; // 아직 시간 안됨
            }
          }

          // 캠페인 실행
          const result = await this.pushCampaignService.executeScheduledCampaign(schedule);

          if (result.success) {
            this.logger.log(
              `✅ [PushScheduler] 캠페인 실행 성공: scheduleId=${schedule.id}, campaignId=${result.campaignId}, sent=${result.sentCount}`,
            );
          } else {
            this.logger.warn(
              `⚠️ [PushScheduler] 캠페인 실행 실패 또는 중복: scheduleId=${schedule.id}, message=${result.message}`,
            );
          }
        } catch (error) {
          this.logger.error(
            `❌ [PushScheduler] 스케줄 실행 중 에러: scheduleId=${schedule.id}, error=${error.message}`,
            error.stack,
          );
        }
      }

      this.logger.log('✅ [PushScheduler] 스케줄 확인 완료');
    } catch (error) {
      this.logger.error(`❌ [PushScheduler] 스케줄 확인 실패: ${error.message}`, error.stack);
    }
  }

  /**
   * 수동 트리거 (개발/테스트용)
   */
  async triggerScheduleCheck() {
    this.logger.log('🔧 [PushScheduler] 수동 트리거 실행');
    await this.handleScheduledPushes();
    return { success: true, message: '스케줄 확인이 수동으로 트리거되었습니다' };
  }
}
```

- @nestjs/schedule의 @Cron 데코레이터 사용
- KST 타임존 고정
- 1분마다 자동 실행
- 수동 트리거 메서드 제공 (테스트용)

## 🎯 작업 7 핵심 인사이트

### 1. 3계층 아키텍처의 중요성
- **Schedule (설정)** → **Campaign (실행 이력)** → **Log (개별 발송)**
- 명확한 책임 분리로 확장성 확보
- 통계 집계가 용이 (스케줄별, 캠페인별, 로그별)

### 2. campaignKey를 통한 멱등성 보장
- 같은 스케줄이 동시에 여러 번 실행되는 것을 방지
- DB unique constraint로 중복 방지
- Format: `schedule-${scheduleId}-${timestamp}`

### 3. ONCE 스케줄의 자동 비활성화
- 실행 후 자동 비활성화로 재실행 방지
- 수동으로 다시 활성화하여 재사용 가능
- 실수로 인한 중복 발송 원천 차단

### 4. Cron 표현식의 유연성
- 단순 시간 지정부터 복잡한 주기까지 표현 가능
- 크론 표현식 생성 도구 링크 제공으로 사용성 향상
- 서버 타임존 고정 (Asia/Seoul)으로 혼란 방지

### 5. 통계 필드의 실시간 업데이트
- 스케줄별로 실행 통계 자동 집계
- 운영팀이 성공률 모니터링 가능
- 향후 자동 알림/대시보드 구현 기반

### 6. 관리자 UI의 직관성
- 4개 탭으로 용도별 명확히 분리
- 스케줄 목록에서 바로 토글/삭제 가능
- 실행 통계 시각화로 한눈에 파악

## 🚀 향후 개선 방향

### 1. 타겟팅 쿼리 Builder UI
- 현재: targetQuery를 JSON으로 직접 입력
- 개선: GUI로 조건 선택 (성별, 연령, 지역, 활동 내역 등)
- 예시: "30대 남성 + 최근 7일 미활동 + 서울 거주"

### 2. A/B 테스트 기능
- 제목/본문 여러 버전 동시 발송
- 오픈율/클릭율 자동 집계
- 승자 자동 선택 및 대량 발송

### 3. 캠페인 대시보드
- 실시간 발송 진행률
- 스케줄별 성공률 차트
- 알림 실패 원인 분석

### 4. 스케줄 템플릿
- 자주 사용하는 설정을 템플릿으로 저장
- 원클릭 스케줄 생성
- 예시: "매일 아침 9시 리마인더", "매주 금요일 이벤트"

### 5. 실행 이력 상세 조회
- 특정 캠페인의 로그 조회 (누구에게, 언제, 성공/실패)
- 실패 원인별 통계
- 재발송 기능
