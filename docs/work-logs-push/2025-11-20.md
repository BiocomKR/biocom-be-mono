## 📋 작업 1: Rate Limiting 구현

### 문제 상황
- 푸시 API에 아무런 Rate Limit이 없어 **무분별한 발송 가능**
- 특히 전체 발송 API(`/push/notifications/send-to-all`)는 한 번의 요청으로 수천 건의 푸시가 발송되는데, **제한이 전혀 없음**
- 악의적인 사용자나 버그로 인한 반복 호출 시 **FCM 비용 폭증** 가능

```typescript
async getPushLogs(query: PushLogQueryDto): Promise<PushLogListResponseDto> {
  const { page = 1, limit = 100, userId, success, type } = query;
  
  // 필터 조건 구성
  const where: any = {};
  if (userId !== undefined) where.userId = userId;
  if (success !== undefined) where.success = success;
  if (type) where.type = type;
  
  // 로그 조회 (최신순)
  const logs = await this.prisma.pushNotificationLog.findMany({
    where, skip: (page - 1) * limit, take: limit, orderBy: { sentAt: 'desc' },
  });
  
  return { logs, total, page, limit, totalPages };
}
```

## 📋 작업 3: 토큰 중복 검증 강화

### 문제 상황

현재 PushToken 테이블의 Unique 제약:
```prisma
@@unique([userId, deviceId, provider])
```

**문제 시나리오**:
1. 유저가 디바이스 X에서 앱 설치 → FCM 토큰 `TOKEN123` 발급
2. `userId=1, deviceId=X, token=TOKEN123` 저장
3. 유저가 앱 삭제 후 재설치 → FCM이 **같은 토큰** `TOKEN123` 재사용
4. 클라이언트가 실수로 `deviceId=Y`로 전송
5. **결과**: 동일한 토큰이 두 개의 deviceId에 중복 저장 → **푸시 2번 발송**

### 구현 내용

**파일**: `src/push/services/push-token.service.ts` **(38-68번 줄)**

```typescript
async registerToken(userId: number, dto: RegisterPushTokenDto) {
  const { token, deviceId, platform } = dto;

  // 1. 동일한 토큰이 다른 deviceId에 등록되어 있는지 확인 (38-48번 줄)
  const existingTokenWithSameValue = await this.prisma.pushToken.findFirst({
    where: {
      token,
      provider: 'FCM',
      isActive: true,
      NOT: { deviceId: deviceId || token },
    },
  });

  // 2. 중복 발견 시 기존 토큰 비활성화 (50-68번 줄)
  if (existingTokenWithSameValue) {
    this.logger.warn(`⚠️ 동일 토큰이 다른 디바이스에 존재`);
    
    await this.prisma.pushToken.update({
      where: { id: existingTokenWithSameValue.id },
      data: {
        isActive: false,
        invalidatedAt: new Date(),
        invalidReason: 'TOKEN_REASSIGNED_TO_NEW_DEVICE',
      },
    });
  }

  // 3. 새로운 토큰 등록 (70-97번 줄, 기존 upsert 로직)
  const pushToken = await this.prisma.pushToken.upsert({ ... });
  return this.mapToResponseDto(pushToken);
}
```

### 동작 흐름 예시

**현재 DB**: `id=1, userId=10, deviceId=X, token=TOKEN123, isActive=true`

**새 요청**: `{ token: "TOKEN123", deviceId: "Y" }`

**검증 실행**: 같은 TOKEN123을 가진, 하지만 deviceId가 Y가 아닌 토큰 찾기 → id=1 발견

**기존 토큰 비활성화**: `UPDATE push_tokens SET isActive=false, invalidReason='TOKEN_REASSIGNED_TO_NEW_DEVICE' WHERE id=1`

**새 토큰 등록**: `id=2, userId=10, deviceId=Y, token=TOKEN123, isActive=true`

**최종 DB 상태**:
```
id=1, deviceId=X, token=TOKEN123, isActive=false  ← 비활성화
id=2, deviceId=Y, token=TOKEN123, isActive=true   ← 새로 등록
```

### 효과
- ✅ 중복 푸시 완전 차단
- ✅ 데이터 정합성 향상
- ✅ `invalidReason`으로 추적 가능

## 📋 작업 4: Topic 기반 푸시 인프라 세팅

### 배경: FCM Topic이란?

**일반 방식**: 유저 1000명에게 발송 → 1000개 토큰 조회 → FCM 1000번 호출

**Topic 방식**: "marketing" 토픽 구독자에게 1번만 발송 → FCM이 알아서 배포

**활용 예시**:
- `all-users`: 전체 공지사항
- `marketing`: 마케팅 동의 유저
- `event-123`: 특정 이벤트 참여자
- `inactive-7days`: 7일간 미접속 유저

```typescript
@Injectable()
export class PushTopicService {
  // Topic 구독 (30-63번 줄)
  async subscribeTopic(userId: number, dto: SubscribeTopicDto) {
    const tokens = dto.tokens || await this.getUserActiveTokens(userId);
    const success = await this.fcmProvider.subscribeToTopic(tokens, dto.topic);
    return { success, message: `${dto.topic} 토픽에 구독되었습니다` };
  }

  // Topic 구독 해제 (72-103번 줄)
  async unsubscribeTopic(userId: number, dto: UnsubscribeTopicDto) {
    const tokens = dto.tokens || await this.getUserActiveTokens(userId);
    const success = await this.fcmProvider.unsubscribeFromTopic(tokens, dto.topic);
    return { success, message: '구독이 해제되었습니다' };
  }

  // Topic으로 푸시 전송 (112-136번 줄)
  async sendToTopic(dto: SendPushToTopicDto) {
    const result = await this.fcmProvider.sendToTopic(dto.topic, { ... });
    return { success: result.success, messageId: result.messageId };
  }

  // 유저의 활성 토큰 조회 (145-161번 줄)
  private async getUserActiveTokens(userId: number): Promise<string[]> {
    const pushTokens = await this.prisma.pushToken.findMany({
      where: { userId, isActive: true, provider: 'FCM' },
    });
    return pushTokens.map((pt) => pt.token);
  }
}
```

## 🎯 핵심 인사이트

### 1. Rate Limiting은 필수
- 특히 금전적 비용이 드는 API는 **반드시 보호 필요**
- 전체 발송은 1시간/1번으로 **가장 엄격하게 제한**

### 2. 로그는 운영의 생명줄
- 로그 조회 API는 **기능 개발과 동시에** 만들어야 함
- 페이지네이션은 **처음부터** 넣어야 나중에 고생 안 함

### 3. 데이터 정합성은 서비스 레벨에서 보장
- DB 제약만으로는 **복잡한 비즈니스 로직 처리 불가**
- 감사 추적을 위해 **삭제보다 비활성화**가 나음

### 4. 인프라는 미리 준비
- Topic 같은 인프라는 **사용 전에 미리 세팅**
- 지금 시간 투자가 **나중에 시간 절약**

### 5-1. PushNotificationType enum 일원화

**문제 상황**:
- `PushNotificationLog.type` 필드에 임의의 문자열 저장 가능 (`message.data.type` 값 혼용)

**해결 방법**:

```typescript
async updatePushLogStatus(
  userId: number,
  logId: number,
  status: 'READ' | 'CLICKED',
) {
  // 1. 로그 조회 및 권한 확인
  const log = await this.prisma.pushNotificationLog.findFirst({
    where: { id: logId, userId },
  });

  if (!log) {
    return { success: false, message: '푸시 알림을 찾을 수 없습니다' };
  }

  // 2. 상태에 따라 업데이트
  const updateData: any = {};
  if (status === 'READ' && !log.readAt) {
    updateData.readAt = new Date();
  } else if (status === 'CLICKED' && !log.clickedAt) {
    updateData.clickedAt = new Date();
    // CLICKED는 READ를 포함하므로 readAt도 함께 설정
    if (!log.readAt) {
      updateData.readAt = new Date();
    }
  }

  // 이미 업데이트된 경우 중복 처리 방지
  if (Object.keys(updateData).length === 0) {
    return { success: true, message: '이미 처리된 상태입니다' };
  }

  // 3. 업데이트 실행
  await this.prisma.pushNotificationLog.update({
    where: { id: logId },
    data: updateData,
  });

  return { success: true, message: '푸시 상태가 업데이트되었습니다' };
}
```

**주요 로직**:
- userId 권한 검증 (다른 유저의 로그 수정 불가)
- CLICKED 시 readAt도 자동 설정
- 중복 업데이트 방지 (idempotent)

### 6-2. FCM Provider 인터페이스 불일치 버그 수정

**문제 상황**:

- 하지만 FCM Provider는 여전히 **객체를 기대** (`const { token } = tokenData;`)
- push-notification.service.ts는 **문자열로 전달** (`pushToken.token`)
- 결과: 구조 분해 할당 실패 → `token = undefined`

**해결 방법**:

#### 1️⃣ FCM Provider 시그니처 변경

```typescript
async sendToToken(
  tokenData: any,  // ❌ 객체 기대
  message: PushMessage,
): Promise<PushSendResult> {
  const { token } = tokenData;  // ❌ 구조 분해 할당
```

**변경 후**:
```typescript
async sendToToken(
  token: string,  // ✅ 문자열 직접 받음
  message: PushMessage,
): Promise<PushSendResult> {
  // token 직접 사용
```

#### 2️⃣ Push Test Service 수정

**변경 후**:
```typescript
const result = await this.fcmProvider.sendToToken(
  token,  // ✅ 문자열로 전달
  { title, body },
```

#### 3️⃣ Provider Interface 업데이트

## 🎯 작업 6 핵심 인사이트

### 1. 자동 로그인 시나리오는 놓치기 쉬운 엣지 케이스
- 일반적인 로그인 플로우만 테스트하면 발견 못함
- 실제 사용자 시나리오 기반 테스트 필요
- 앱 시작 시점에 필수 초기화 로직 체크리스트 필요

### 2. Schema 변경 시 전체 영향 범위 확인 필수
- 단순히 DB 필드만 바꾸면 안됨
- Interface, Service, Provider 모든 레이어 점검
- TypeScript `any` 타입은 이런 버그를 숨김 (string으로 명시해야 컴파일 타임에 잡힘)

### 3. 디버그 로그는 사전 예방
- 버그 발생 후 로그 추가하면 늦음
- 중요한 데이터 흐름에는 미리 로그 심어두기
- `token?.substring(0, 20)` 같은 안전한 로깅 패턴 사용

### 4. 테스트 환경과 프로덕션 환경 설정 분리
- 개발 시 편의성과 운영 안정성은 트레이드오프
- 환경변수로 분리하거나 명확히 주석 필요
