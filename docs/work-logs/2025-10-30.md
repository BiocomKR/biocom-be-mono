### 2. 챌린저 주차별 접근 제어 구현
**배경**:
- 챌린저는 현재 챌린지 진행 일차(currentDay)에 따라 접근 가능한 주차가 제한되어야 함
- 구독자는 모든 주차에 자유롭게 접근 가능

**구현 로직**:
```typescript
// 챌린저 주차별 접근 제어
if (!isSubscriber && week) {
  const activeChallenge = await this.prisma.userChallenge.findFirst({
    where: { userId, status: 'ACTIVE' },
    select: { activatedAt: true }
  });

  if (activeChallenge) {
    const { calculateChallengeDay } = await import('../common/utils/kst-date.util');
    const currentDay = calculateChallengeDay(activeChallenge.activatedAt);
    const allowedWeek = Math.ceil(currentDay / 7);

    if (week > allowedWeek) {
      this.logger.log(`챌린저 접근 제한 - ${week}주차 조회 불가 (현재 ${currentDay}일차)`);
      return []; // 403 에러 대신 빈 배열 반환
    }
  }
}
```

**접근 제어 규칙**:
- 챌린지 1~7일차: 1주차만 접근 가능
- 챌린지 8~14일차: 1~2주차 접근 가능
- 챌린지 15~21일차: 1~3주차 접근 가능
- 구독자: 모든 주차 접근 가능 (우선순위)
- 허용 범위 초과 시: 403 에러 대신 빈 배열 `[]` 반환

**활용 유틸리티**:
- [kst-date.util.ts](../src/common/utils/kst-date.util.ts) - `calculateChallengeDay()` 함수 활용

### 3. Content API 분리 (칼럼 vs 강의)
**배경**:
- 기존 통합 Content 상세 API에서 칼럼과 강의의 차이가 커서 분기 처리가 복잡해짐
- 칼럼과 강의는 요구사항이 많이 다름:
  - 칼럼: 이전글/다음글 네비게이션 필요, 퀴즈 없음
  - 강의: 퀴즈 정보 포함, 구독자/챌린저만 접근 가능

**새로운 API 구조**:
1. **칼럼 상세 조회** - `GET /api/contents/columns/:id`
   - JWT 인증만 필요 (ALL)
   - 이전글/다음글 네비게이션 정보 포함
   - Type validation: COLUMN 타입만 허용

2. **강의 상세 조회** - `GET /api/contents/lectures/:id`
   - JWT 인증 + 구독자/챌린저 체크 (CHALLENGE_OR_SUB)
   - 연결된 퀴즈 정보 포함 (lectureQuizzes)
   - 챌린지 상품 정보 포함
   - Type validation: LECTURE 타입만 허용

3. **기존 API 유지** - `GET /api/contents/:id` (Deprecated)
   - 하위 호환성을 위해 유지하되 Swagger에 deprecated 표시

**Service Layer 타입 검증 추가**:
```typescript
// getColumnById()
if (content.type !== 'COLUMN') {
  throw new BadRequestException(`해당 컨텐츠는 칼럼이 아닙니다: ${id}`);
}

// getLectureById()
```

### 4. 챌린지 상품 필터링 구현
**배경**:
- 강의는 어떤 챌린지에 속하는지 구분되어야 함 (예: 이너뷰티 챌린지, 다이어트 챌린지)
- 이는 "사용자가 어떤 챌린지를 하고 있냐"가 아니라 "어떤 챌린지의 강의를 보여줄 것이냐"에 대한 필터링
- DB 구조: `contents.challengeId` → `products.id` (categoryCode='CHALLENGE')

**구현 로직**:
```typescript
// productId 파라미터가 없으면 첫 번째 CHALLENGE 상품을 기본값으로 사용
let finalChallengeId = challengeId;

if (!finalChallengeId) {
  const defaultChallenge = await this.prisma.product.findFirst({
    where: {
      categoryCode: 'CHALLENGE',
      status: 'ACTIVE' // 주의: isActive가 아닌 status 사용
    },
    select: { id: true },
    orderBy: { id: 'asc' }
  });

  if (!defaultChallenge) {
    throw new NotFoundException('활성화된 챌린지 상품이 없습니다');
  }

  finalChallengeId = defaultChallenge.id;
}

// WHERE 조건에 challengeId 정확히 일치하는 것만
const where: any = {
  type: 'LECTURE',
  isActive: true,
  challengeId: finalChallengeId // 정확히 일치해야 함
};
```

**API 사용 예시**:
- `GET /api/contents/lectures?week=1&productId=38` → 이너뷰티 챌린지(38번)의 1주차 강의
- `GET /api/contents/lectures?week=1` → 첫 번째 활성 챌린지의 1주차 강의 (기본값)

**데이터 정합성**:
- 기존 강의 데이터의 `challengeId`를 38(이너뷰티 챌린지)로 업데이트 완료
- 추후 데이터 추가 시 `challengeId` 필수 입력 규칙 적용 예정

## 🐛 해결된 에러

### Error 1: accessLevel 컬럼 존재하지 않음
```
Unknown argument `accessLevel`. Available options are marked with ?.
```
**원인**: DB에서 삭제된 컬럼을 코드에서 계속 사용
**해결**: accessLevel 관련 모든 로직 제거

### Error 2: Quiz.contentFiles 관계 존재하지 않음
```
Unknown field `contentFiles` for include statement on model `Quiz`
```
**원인**: Quiz 모델은 missionQuizzes, lectureQuizzes, quizAttempts 관계만 있음
**해결**: contentFiles include 제거, quiz만 include

### Error 3: req.user.userId undefined
```
Argument `where` of type UserWhereUniqueInput needs at least one of `id` or `email` arguments.
```
**원인**: JWT payload는 `sub`로 user ID 저장, `userId` 아님
**해결**: `req.user.userId` → `req.user.sub` 변경

### Error 4: Product.isActive 필드 존재하지 않음
```
Unknown argument `isActive`. Available options are marked with ?.
```
**원인**: Products 테이블은 `status` 컬럼 사용 ('ACTIVE', 'INACTIVE' 등)
**해결**: `isActive: true` → `status: 'ACTIVE'` 변경

### Error 5: Controller에서 result.lectures 참조 에러
```
Cannot read properties of undefined (reading 'length')
```
**원인**: Service가 직접 배열 반환하는데 Controller에서 객체로 래핑된 것으로 가정
**해결**: `result.lectures` → `lectures` 변경

## 📝 주요 의사결정

### 1. 빈 배열 vs 403 에러
- **결정**: 챌린저가 접근 불가능한 주차 요청 시 빈 배열 `[]` 반환
- **이유**: UX 관점에서 에러보다 부드러운 처리, 프론트엔드에서 "아직 접근할 수 없습니다" 메시지 표시 가능

### 2. challengeId 정확 일치 vs null 허용
- **결정**: challengeId가 정확히 일치하는 것만 조회, null fallback 없음
- **이유**: 기존 데이터 업데이트 완료, 추후 필수 필드로 관리 예정

### 3. 기본 챌린지 선택 방식
- **결정**: productId 미제공 시 첫 번째 CHALLENGE 상품을 기본값으로 사용 (`orderBy: { id: 'asc' }`)
- **이유**: 하드코딩 방지, 확장 가능성 고려

### 4. 구독자 vs 챌린저 우선순위
- **결정**: 사용자가 구독자이면서 동시에 챌린저인 경우 구독자 권한 우선 (제한 없음)

### 6. 강의 상세 API 플레이리스트 기능 추가
**배경**:
- 피그마 디자인을 분석한 결과, 강의 상세 화면에서 같은 주차의 다른 강의 목록이 필요함
- 사용자가 뒤로가기로 목록으로 이동하지 않고 한 화면에서 다음 영상을 볼 수 있도록 함
- 형님이 선행작업으로 강의별 썸네일/동영상 URL 데이터를 `content_files` 테이블에 등록 완료

**구현 로직**:
```typescript
// 같은 주차의 다른 강의 목록 조회 (플레이리스트)
const playlist = await this.prisma.content.findMany({
  where: {
    type: 'LECTURE',
    isActive: true,
    weekNumber: content.weekNumber,      // 현재 강의와 같은 주차
    challengeId: content.challengeId,    // 현재 강의와 같은 챌린지
  },
  select: {
    id: true,
    title: true,
    dayNumber: true,
    weekNumber: true,
    contentFiles: {
      where: {
        file: {
          mimeType: {
            startsWith: 'image/'  // 썸네일 이미지만
          }
        }
      },
      include: {
        file: true
      },
      orderBy: { sortOrder: 'asc' },
      take: 1, // 썸네일 1개만
    },
  },
  orderBy: { dayNumber: 'asc' },  // 일차 순으로 정렬
});

return {
  ...content,
  playlist,  // 플레이리스트 추가
};
```

- `dayNumber` 순으로 정렬 (0, 1, 2, 3, ...)
- 각 강의마다 썸네일 이미지 1개 포함 (GCS URL)
- 제목, ID, 주차, 일차 정보 포함

### 7. GCS 파일 업로드 재시도 로직 추가
**배경**:
- 스웨거에서 연속적으로 파일 업로드 시 간헐적으로 400 에러 발생
- 첫 번째 업로드 성공 → 두 번째 업로드 무조건 실패 → 재시도하면 성공하는 패턴
- GCS API 타이밍 이슈로 추정

**구현 로직**:
```typescript
private async uploadToGoogleStorage(
  fileBuffer: Buffer,
  fileName: string,
  mimeType: string,
  maxRetries: number = 3  // 최대 3번 재시도
): Promise<string> {
  let lastError: any;

  for (let attempt = 1; attempt <= maxRetries; attempt++) {
    try {
      const bucket = this.storage.bucket(this.bucketName);
      const file = bucket.file(fileName);

      await file.save(fileBuffer, {
        metadata: { contentType: mimeType },
        public: true,
      });

      const publicUrl = `https://storage.googleapis.com/${this.bucketName}/${fileName}`;

      if (attempt > 1) {
        this.logger.log(`GCS 업로드 성공 (${attempt}번째 시도): ${publicUrl}`);
      } else {
        this.logger.log(`GCS 업로드 완료: ${publicUrl}`);
      }

      return publicUrl;

    } catch (error) {
      lastError = error;
      this.logger.warn(`GCS 업로드 실패 (${attempt}/${maxRetries}번째 시도): ${error.message}`);

      // 마지막 시도가 아니면 재시도 전 대기
      if (attempt < maxRetries) {
        const delayMs = Math.pow(2, attempt - 1) * 1000; // 지수 백오프: 1초, 2초, 4초
        this.logger.log(`${delayMs}ms 후 재시도합니다...`);
        await new Promise(resolve => setTimeout(resolve, delayMs));
      }
    }
  }

  // 모든 재시도 실패
  this.logger.error(`GCS 업로드 최종 실패 (${maxRetries}번 시도)`, lastError);
  throw new BadRequestException('파일 업로드 중 오류가 발생했습니다. 잠시 후 다시 시도해주세요.');
}
```

**재시도 전략**:
1. **최대 재시도 횟수**: 3번
2. **지수 백오프 (Exponential Backoff)**:
   - 1번째 실패 → 1초 대기 후 재시도
   - 2번째 실패 → 2초 대기 후 재시도
   - 3번째 실패 → 4초 대기 후 재시도
3. **상세 로깅**:
   - 첫 시도 성공: "GCS 업로드 완료"
   - 재시도 후 성공: "GCS 업로드 성공 (N번째 시도)"
   - 각 실패: "GCS 업로드 실패 (N/3번째 시도)"
   - 최종 실패: "GCS 업로드 최종 실패 (3번 시도)"
4. **사용자 친화적 에러 메시지**: "잠시 후 다시 시도해주세요"

**시도한 방법과 실패 원인**:
- ❌ **GCS Storage 클라이언트 `autoRetry` 옵션**: TypeScript에서 해당 옵션 미지원 (빌드 에러)
- ✅ **수동 재시도 로직 구현**: 직접 for문으로 재시도 로직 구현 (성공)

**장점**:
- 일시적인 네트워크 지연이나 GCS API 타이밍 이슈를 자동으로 해결
- 사용자가 수동으로 재시도할 필요 없음
- 상세한 로그로 문제 추적 가능

### 8. 강의 상세 API 보안 강화 (일차별 접근 제어 및 퀴즈 노출 조건)
**배경**:
- 형님이 발견한 보안 이슈:
  1. 챌린저가 1일차인데 3주차 강의 ID(19번)를 직접 URL로 접근하면 볼 수 있음
  2. 퀴즈는 무조건 챌린지 진행일과 정확히 일치할 때만 노출되어야 함

**문제점**:
- 기존 로직은 구독자/챌린저 여부만 체크하고 주차/일차 제한이 없었음
- 챌린저가 미래의 강의를 URL로 직접 접근 가능 (보안 취약점)

**해결 방안**:
```typescript
// 챌린저의 경우 진행 주차 체크
let currentDay: number | null = null;
if (!isSubscriber && hasActiveChallenge) {
  const { calculateChallengeDay } = await import('../common/utils/kst-date.util');
  currentDay = calculateChallengeDay(user.userChallenges[0].activatedAt);
  const allowedWeek = Math.ceil(currentDay / 7);

  // 챌린저는 현재 주차 이하의 강의만 접근 가능
  if (lecture.weekNumber > allowedWeek) {
    this.logger.warn(`강의 접근 제한 - 사용자 ID: ${req.user.sub}, 현재 ${currentDay}일차(${allowedWeek}주차), 요청 강의: ${lecture.weekNumber}주차`);
    throw new ForbiddenException(`아직 접근할 수 없는 강의입니다. 현재 ${allowedWeek}주차까지 이용 가능합니다.`);
  }

  this.logger.log(`챌린저 주차 체크 완료 - 현재: ${currentDay}일차(${allowedWeek}주차), 강의: ${lecture.weekNumber}주차`);
}

// 퀴즈는 챌린저의 경우 currentDay와 정확히 일치할 때만 노출
let lectureData = { ...lecture };
if (!isSubscriber && hasActiveChallenge && currentDay !== null) {
  if (lecture.dayNumber !== currentDay) {
    // 현재 일차와 일치하지 않으면 퀴즈 제거
    lectureData = {
      ...lecture,
      lectureQuizzes: [],
    };
    this.logger.log(`퀴즈 미노출 - 현재 ${currentDay}일차, 강의 ${lecture.dayNumber}일차 (불일치)`);
  } else {
    this.logger.log(`퀴즈 노출 - 현재 ${currentDay}일차, 강의 ${lecture.dayNumber}일차 (일치)`);
  }
}
```

**접근 제어 규칙**:

1. **강의 접근 (주차 단위)**:
   - 2일차 챌린저 (allowedWeek = 1): 1주차 전체 강의(1~8번) 접근 가능 ✅
   - 8일차 챌린저 (allowedWeek = 2): 1~2주차 전체 강의 접근 가능 ✅
   - 2일차 챌린저가 3주차 강의(19번) 접근 시도: 403 에러 ❌

2. **퀴즈 노출 (일차 단위)**:
   - 2일차 챌린저가 2일차 강의(dayNumber=2) 조회: 퀴즈 노출 ✅
   - 2일차 챌린저가 1일차 강의(dayNumber=1) 조회: 퀴즈 미노출 (빈 배열) ❌
   - 2일차 챌린저가 3일차 강의(dayNumber=3) 조회: 퀴즈 미노출 (빈 배열) ❌

3. **구독자 권한**:
   - 모든 주차, 모든 강의, 모든 퀴즈 접근 가능 (제한 없음)

**트러블슈팅**:
- **초기 구현 실수**: `lecture.dayNumber > currentDay`로 일차 단위 체크
  - 문제: 2일차 챌린저가 4일차 강의를 못 보는 문제 발생
  - 형님 피드백: "응?? 강의 1주차는 다 나와야 하는데?"
- **수정**: `lecture.weekNumber > allowedWeek`로 주차 단위 체크
  - 결과: 같은 주차 내 모든 강의 접근 가능 ✅

## 💡 오늘의 핵심 배운 점

### 1. 접근 제어의 단위 이해
- **강의 목록/상세 접근**: 주차 단위 제어 (같은 주차는 모두 접근 가능)
- **퀴즈 노출**: 일차 단위 제어 (정확히 일치해야 노출)
- 비즈니스 요구사항에 따라 제어 단위가 다를 수 있음

### 2. 보안 이슈의 중요성
- API 엔드포인트가 있으면 URL로 직접 접근 가능
- 목록에서 안 보인다고 접근이 차단되는 것이 아님
- 상세 API에도 반드시 접근 제어 로직 필요

### 3. 빌드 에러의 영향
- TypeScript 빌드 에러 발생 시 서버가 재시작되지 않음
- 코드 수정이 적용되지 않아 테스트 결과가 이상하게 나올 수 있음
- 항상 빌드 에러를 먼저 확인하고 테스트할 것
