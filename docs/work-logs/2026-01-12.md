### 3. 원인 분석

#### 3.1 직접 원인

#### 3.2 근본 원인: Cloud SQL Authorized Networks 누락

**GKE 클러스터 노드 현황:**
| 노드 | External IP | Cloud SQL 등록 | DB 연결 |
|------|-------------|----------------|---------|
| `gke-biocom-cluster-prod-default-pool-f9f15a6e-kf6k` | `34.50.62.35` | O (기존 등록) | 성공 |
| `gke-biocom-cluster-prod-default-pool-f9f15a6e-1h4u` | `34.64.200.95` | X (누락) | **실패** |

- Cloud SQL `biocom-postgres-prod`의 Authorized Networks에 노드 `1h4u`의 IP가 등록되어 있지 않았음
- CronJob이 `1h4u` 노드에 배치될 경우 DB 연결 실패 (P1001 에러)
- API 서비스는 주로 `kf6k` 노드에서 처리되어 정상 작동

### 6. 구조적 문제점 및 개선 방안

#### 6.1 현재 구조의 문제점

현재 Cloud SQL 접근 방식:
- GKE 노드의 **External IP** 기반 접근
- 각 노드 IP를 Cloud SQL Authorized Networks에 수동 등록 필요

**오토스케일링 시 발생 가능한 문제:**
1. 트래픽 폭증 → GKE 오토스케일러가 새 노드 자동 생성
2. 새 노드의 External IP는 Cloud SQL에 등록되어 있지 않음
3. 새 노드에 배치된 Pod들 전부 DB 연결 실패
4. **트래픽 많을 때 서비스 장애** (최악의 타이밍)

> **"스케일링 할수록 장애가 커지는 구조"**

#### 6.2 개선 방안 비교

| 방안 | 설명 | 장점 | 단점 | 권장 |
|------|------|------|------|------|
| **Private IP 전환** | VPC 내부 통신 | 노드 추가에 독립적, 보안 우수 | VPC 피어링 설정 필요 | **권장** |
| Cloud SQL Auth Proxy | 사이드카로 IAM 인증 | IP 허용 불필요 | 리소스 오버헤드 | 고려 |
| 0.0.0.0/0 허용 | 모든 IP 허용 | 간단함 | 보안 위험 | **비권장** |

#### 6.3 Private IP 전환 방법 (참고)

```bash
# 1. Cloud SQL Private IP 활성화 확인
gcloud sql instances describe biocom-postgres-prod \
  --project=api-prod-biocom \
  --format="yaml(ipAddresses)"

# 2. Private IP가 없으면 활성화
gcloud sql instances patch biocom-postgres-prod \
  --project=api-prod-biocom \
  --network=projects/api-prod-biocom/global/networks/default \
  --no-assign-ip  # Public IP 비활성화 (선택사항)

# 3. ConfigMap의 DB_HOST를 Private IP로 변경
kubectl edit configmap biocom-api-config -n biocom-api
# DB_HOST: 10.x.x.x (Private IP)
```
