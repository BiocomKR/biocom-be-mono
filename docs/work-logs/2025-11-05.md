### 3. API 구조 개선 (3개 → 2개)

#### 기존 구조 (삭제됨)
- ❌ `POST /api/phone-verification/identity` - 1단계만
- ❌ `POST /api/phone-verification/sms` - 2단계만
- ❌ `POST /api/phone-verification/confirm` - 3단계만

#### 새로운 구조 (최종)
- ✅ `POST /api/phone-verification/request` - **본인인증 요청**
  - KCP 1단계(실명확인) 호출
  - DB에 응답값 저장 (per_cert_no 포함)
  - KCP 2단계(SMS발송) 자동 호출 (per_cert_no 바인딩)
  - 클라이언트에 per_cert_no 반환

- ✅ `POST /api/phone-verification/verify` - **인증번호 검증**
  - KCP 3단계(OTP확인) 호출
  - CI/DI 값 반환

```typescript
async requestVerification(dto: RequestVerificationDto) {

  // 2. DB 저장 (per_cert_no 포함)

  // 3. KCP 2단계 (SMS발송) API 호출

    per_cert_no: step1Response.per_cert_no, // 1단계 결과 바인딩
    ...
  });

  // 4. per_cert_no 반환
  return { certNumber: step1Response.per_cert_no, ... };
}

async verifyOtp(dto: VerifyOtpDto) {
  // KCP 3단계 (OTP확인) API 호출
  const response = await this.kcpApiService.confirmOtp({ ... });

  // CI/DI 반환
  return { ci: response.CI, di: response.DI, ... };
}
```

## 🎯 핵심 인사이트

### 1. KCP API 3단계 프로세스
```
1단계 (tx_type: 2100) - 실명 확인
  ↓ per_cert_no 발급
2단계 (tx_type: 2200) - SMS 발송 (per_cert_no 필요)
  ↓ SMS 전송
3단계 (tx_type: 2300) - OTP 확인 (per_cert_no + OTP 필요)
  ↓ CI/DI 발급
```

### 2. 서명 생성 규칙
```javascript
// 1단계, 2단계 서명
phone_no^birth_day^user_name^local_code^sex_code

// 주의: local_code는 지역코드 (01:내국인)이며, 통신사 코드(comm_id)가 아님!

// 3단계 서명
per_cert_no^cert_otp_no
```

### 3. 중요 파라미터
- `local_code`: **지역코드** (01:내국인, 02:외국인)
- `comm_id`: **통신사코드** (SKT, KTF, LGT, SKM, KTM, LGM)
- `pay_method`: 반드시 `"CERT:PERSON"`
- `kcp_cert_info`: PEM 인증서 직렬화 (\r\n → \n)

## 💡 교훈

1. **API 가이드 문서를 정확히 따라야 한다**
   - 필수 파라미터를 하나라도 빠뜨리면 포맷 오류 발생
   - 파라미터 이름과 값을 정확히 매칭해야 함

2. **직접 테스트가 중요하다**
   - HTTP 파일로 직접 호출하여 문제 원인 파악
   - 코드를 거치지 않고 순수 API 테스트로 검증

3. **API 설계는 사용성 우선**
   - 클라이언트 입장에서 가장 간단한 구조가 최선
   - 3개 API → 2개 API로 단순화

4. **서명 생성 로직 검증**
   - local_code vs comm_id 혼동 주의
   - 서명 대상 데이터 정확히 조합
