```typescript
async issueBillingKey(authKey: string, customerKey: string): Promise<string> {
```

### 7. 무료 아이템 지급 방식 논의 🎁

**형님 고민**:
> "지금 0원결제를 해야할 상황이 왔어. 챌린지이용권이야. 이거 0원에 판매하는거라고 하네. 근데 또 무형의 상품이야. 이럴때 이거 인앱결제를 태워야 하는게 맞냐?"

**조사 결과**:

#### 애플 정책:
- 디지털 콘텐츠 = 무조건 인앱결제 (유료든 무료든)
- 과거에는 0원 인앱결제가 안 됐음
- 현재는 가능해진 것 같으나 버그가 많음

#### 대안:
1. **프로모션 코드** (애플 공식)
   - 100개 코드/아이템, 총 1000개/6개월
   - 28일 만료
   - 제한적

2. **서버에서 직접 지급**
   - ❌ 위험: 애플이 리젝할 수 있음
   - 회원 전용 콘텐츠는 예외 가능

3. **0원 인앱결제**
   - 가능하긴 한데 버그 많음

**형님의 해결책** 💡:
> "화면에서 챌린지 이용권 구매 라는 기능이 있어서 0 원 결제를 생각했는데, 생각해보니까 구매 라는 단어 빼고, 챌린지 이용권 획득하기 라고 말만 바꾸면 상관없겠네 ㅋㅋ"

```

→ 0원 결제? 인앱결제? 애매함
```

## 🎯 핵심 인사이트

### 1. 구독 시스템은 단순할수록 좋다
- 일시정지/재개 같은 복잡한 기능은 불필요
- 구독 = 30일 유효, 취소 = 환불 없음
- 이 단순한 로직만으로도 충분함

### 2. 빌링키 발급 플로우를 정확히 이해해야 함
- authKey는 토스에서 일회용으로 발급
- 백엔드가 authKey로 billingKey를 발급받아야 함
- 앱이 billingKey를 알 수는 없음

### 3. API 설계 시 앱 개발자 입장에서 생각
- 추가 API 호출보다는 기존 API에 정보 추가
- 구독 목록 + 빌링키 유무를 한 번에 제공
- 네트워크 호출 최소화

### 4. 무료 아이템은 "획득" 개념으로
- 0원 결제는 기술적으로 복잡함
- 단어 하나 바꾸면 문제 해결
- "구매" → "획득하기"

### 5. 프론트-백엔드 데이터 구조 합의 중요
- 백엔드는 `no: 1-4` 기대
- 프론트는 `no: 5-8` 전송
- 사전 협의 및 명세서 작성 필요

## 💡 교훈

1. **복잡한 기능은 과감히 제거**
   - 일시정지/재개 없이도 충분함
   - "인생이 피곤해진다" - 형님 명언

2. **API 플로우를 정확히 이해하고 구현**
   - authKey → billingKey 발급 플로우
   - 문서만 보지 말고 실제 동작 확인

3. **앱 개발자를 배려한 API 설계**
   - 한 번의 호출로 필요한 정보 모두 제공
   - hasBillingKey를 구독 목록에 포함

4. **단어 선택의 중요성**
   - "구매" vs "획득하기"
   - 단어 하나로 복잡한 문제 해결

5. **프론트-백엔드 명세 합의 필수**
   - outerBeauty no: 1-4 vs 5-8
   - 사전 협의 없으면 버그 발생

6. **버그는 양방향에서 분석**
   - 백엔드만 보지 말고
   - DB 데이터도 확인
   - 프론트 이슈일 수 있음
