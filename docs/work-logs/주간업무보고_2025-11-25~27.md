## 1️⃣ 챌린지 스케줄러 시스템 개선 (11/25~11/26)

### 1.1 배치 실행 주기 최적화

**배경:**
- 기존: 챌린지 활성화 배치가 매일 실행됨
- 문제: 챌린지 시작일은 월요일만 가능 → 불필요한 리소스 낭비
- 추가 문제: 월요일 자정에 여러 배치가 동시 실행되어 경쟁 상태 발생 가능

**해결:**
```
매일      00:00 - 챌린지 만료 처리
월요일    00:05 - 챌린지 활성화 (5분 간격)
월요일    00:10 - 영양제 생성 (5분 간격)
```

**효과:**
- 불필요한 배치 실행 86% 감소 (매일 → 주 1회)
- 경쟁 상태 완전 제거 (5분 간격 보장)
- 리소스 사용 최적화

### 1.2 챌린지 자동 만료 배치 추가

**구현 내용:**
- 매일 자정, endDate가 지난 ACTIVE 챌린지 자동 만료
- 사용자 상태 자동 변경:
  - 활성 구독 있으면 → SUBSCRIBER
  - 활성 구독 없으면 → NEWCOMER

**효과:**
- 수동 만료 처리 불필요
- 사용자 상태 일관성 유지

### 1.3 Kubernetes CronJob 전환

**배경:**
- GKE 멀티 팟 환경에서 NestJS `@Cron` 데코레이터 사용 시 중복 실행 문제
- 예: 팟 3개 → 영양제 데이터 3배 생성

**해결:**
- Kubernetes CronJob 3개 생성 (expire, activate, supplements)
- `concurrencyPolicy: Forbid`로 동시 실행 방지
- main.ts에 CLI 스케줄러 실행 모드 추가

**효과:**
- 멀티 팟 환경에서 단 1개만 실행 보장
- 데이터 중복 생성 완전 차단

**작업 파일:**
- `src/challenge/challenge-scheduler.service.ts`
- `src/main.ts`
- `infra-gcp/k8s/cronjob-*.yaml` (3개)
- `infra-gcp/scripts/02-deploy-app.sh`

## 2️⃣ 영양제 주간 자동 생성 시스템 (11/25~11/26)

### 2.1 영양제 7일치 자동 생성 배치

**개념:**
- 영양제 기록은 다른 기록과 성격이 다름
  - 다른 기록(운동, 식단): 과거 데이터 저장
  - 영양제 기록: **미래 7일간 루틴 예약**

**구현:**
- 매주 월요일 00:10, 챌린지 경험자 대상으로 영양제 7일치 생성
- 사용자별 활성 영양제 루틴(user_supplement_routine) 조회
- 월요일~일요일까지 영양제별 × 7일 데이터 생성 (모두 false 상태)

**예시:**
- 사용자 영양제 3개 → 3 × 7 = 21건 생성
- 초기 상태: morning/afternoon/evening 모두 false

**효과:**
- 사용자가 앱 실행 시 이번 주 영양제 목록 즉시 확인 가능
- 먹었을 때 체크만 하면 되는 UX

### 2.2 영양제 섭취 기록 API

**Endpoint:** `POST /api/tracking/records/supplements/intake`

**주요 기능:**
- 여러 영양제의 아침/점심/저녁 섭취 여부를 한 번에 저장
- 당일 최초 기록 시 사진 업로드 필수
- 당일 최초 기록 시 포인트 100점 자동 지급

**비즈니스 규칙:**
- imageUrl 검증: 기존 기록에 사진 없으면 필수
- 포인트 중복 지급 방지

### 2.3 영양제 루틴 조회 API

**Endpoint:** `GET /api/tracking/records/supplements/routine`

**주요 기능:**
- 사용자의 맞춤 영양제 루틴 목록 조회
- 당일 섭취 기록(morning/afternoon/evening) 포함
- display_order 순서로 정렬

**작업 파일:**
- `src/tracking/services/records.service.ts`
- `src/tracking/controllers/records.controller.ts`
- `src/tracking/dto/supplement-*.dto.ts`

## 3️⃣ 영양제 통계 API 고도화 (11/27)

### 3.1 매트릭스 구조 영양제 통계 API

**Endpoint:** `GET /api/tracking/statistics/supplement?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD`

**데이터 구조:**
- 7일간(월~일) 영양제별 섭취 상태를 2D 매트릭스로 표현
- **파란색 박스**: 루틴에 있고 섭취함 (intakeCount > 0)
- **회색 박스**: 루틴에 있지만 섭취 안함 (intakeCount = 0)
- **빈칸**: 루틴에서 삭제되어 데이터 없음 (null)

**비즈니스 규칙:**
1. 1그룹(isDefault=true) 영양제는 7일 전체 데이터 존재 보장
2. 2,3그룹 영양제는 루틴 추가/삭제에 따라 null 처리
3. 정렬: 현재 user_supplement_routine의 display_order 기준

**응답 예시:**
```json
{
  "supplements": [
    {
      "productId": 4,
      "productName": "바이오 밸런스",
      "displayOrder": 1,
      "dailyStats": [
        { "date": "2025-11-25", "intakeCount": 0, "recommendedCount": 1 },
        { "date": "2025-11-26", "intakeCount": 1, "recommendedCount": 1 }
      ]
    }
  ]
}
```

### 3.2 영양소 섭취 통계 추가

**요구사항:**
- 1그룹(기본) 영양제만 대상
- 영양소별로 주간 섭취량/권장량 계산
- 가나다 순 정렬

**핵심 계산 로직:**

**권장 섭취량 (분모):**
```
recommendedCount = Σ(frequency_per_day) × 7

예) 아연 포함 영양제:
- 바이오밸런스: frequency_per_day = 1
- 클린밸런스: frequency_per_day = 2
→ (1 + 2) × 7 = 21
```

**실제 섭취량 (분자):**
```
intakeCount = Σ(실제 먹은 횟수, 단 하루 권장량 초과 불가)

예) 아연 섭취 (11/25~11/27):
- 바이오밸런스 (freq=1):
  - 11/25: 1회 → min(1, 1) = 1
  - 11/26: 1회 → min(1, 1) = 1
  - 11/27: 1회 → min(1, 1) = 1
  - 합계: 3

- 클린밸런스 (freq=2):
  - 11/25: 2회 → min(2, 2) = 2
  - 11/26: 2회 → min(2, 2) = 2
  - 11/27: 1회 → min(1, 2) = 1
  - 합계: 5

→ 총 섭취량: 3 + 5 = 8 / 21
```

**중요 제약:**
- morning, afternoon, evening 각각 1회로 카운트
- 하루 3번 먹어도 frequency_per_day까지만 인정

**응답 예시:**
```json
{
  "nutrients": [
    {
      "nutrientName": "아연",
      "intakeCount": 8,
      "recommendedCount": 21
    }
  ]
}
```

## 4️⃣ 그래프 DB 기술 검토 (11/28)

### 배경
AI 챗봇 시스템의 토큰 비용 절감을 위한 아키텍처 검토

### 현재 문제점
```
바이오컴 앱 → AI 에이전트 API 호출 → JSON 응답(수 MB)
→ 파싱 + LLM 토큰 주입 (💸 비용 폭탄)
```

**주요 문제:**
1. 데이터 크기: JSON 트래픽 부하
2. 파싱 리소스: CPU/메모리 소모
3. **토큰 비용**: LLM에 전체 JSON 주입 시 토큰 소모 심각 (가장 큰 문제)

### 제안 아키텍처

```
바이오컴 앱 → biocom-api (NestJS)
              ↓ PostgreSQL 저장 (Source of Truth)
              ↓ BullMQ 큐 추가 (비동기)
              ↓
         [Redis Queue]
              ↓
         biocom-mq (별도 프로젝트)
              ↓ Neo4j Driver
              ↓
    [Neo4j Graph Database]
              ↑
    AI 에이전트 (직접 쿼리)
```

### 기술 스택
- **그래프 DB:** Neo4j (2007년부터 성숙)
- **메시지 큐:** BullMQ (기존 프로젝트 사용 경험 있음)
- **배포:** GKE에 2개 Deployment (api + mq)

### 기대 효과
- **토큰 비용 절감:** 80~90% 예상
- **AI 응답 속도:** 2~3배 향상
- **관계 쿼리 속도:** PostgreSQL 대비 10~100배

### 현재 상태
- ✅ 아키텍처 타당성 검증 완료
- ✅ 프로젝트 분리 전략 확정 (biocom-api + biocom-mq)
- ✅ 기술 스택 선정 (Neo4j + BullMQ)
- ⏳ 비용 검토 필요 (Neo4j Aura vs 셀프호스팅)
- ⏳ PoC 일정 및 리소스 확정 대기

**문서:**
- `docs/GRAPH_DB_TECHNICAL_REVIEW.md` (기술 검토 문서)

## 💡 기술적 인사이트

### 1. 경쟁 상태는 시간 간격으로 해결
- 복잡한 락 메커니즘보다 5분 간격이 더 안전하고 단순
- 배치 순서 보장으로 데이터 일관성 확보

### 2. Kubernetes CronJob의 강력함
- 멀티 팟 환경에서 단 1개만 실행 보장
- 애플리케이션 코드 수정 없이 인프라 레벨에서 해결
- `concurrencyPolicy: Forbid`로 동시 실행 방지

### 3. 복잡한 비즈니스 로직의 정밀 구현
- 영양소 계산: 실제 먹은 횟수 기준, Math.min으로 상한 제어
- 매트릭스 구조: null 처리를 통한 루틴 변경 이력 표현
- 정렬 순서: 현재 상태 기준 동적 정렬

### 4. 타임존 일관성의 중요성
- 유틸 함수 활용으로 14개 함수 일괄 수정
- formatKoreanDate() 단일 진실 공급원(Single Source of Truth)
