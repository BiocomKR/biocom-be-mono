## 1. 배치 스케줄러 경쟁 상태 문제 발견 및 해결

### 문제점
월요일 자정에 2개의 배치가 동시 실행되어 경쟁 상태 발생 가능:
- 00:00 - 챌린지 만료 배치
- 00:00 - 챌린지 활성화 배치 (월요일만)

**경쟁 상태 시나리오:**
```
사용자: 챌린지 A 완료(만료 대상) + 챌린지 B 시작 예정

만료 배치: users.status → NEWCOMER
활성화 배치: users.status → CHALLENGER (동시 실행)

결과: 실행 순서에 따라 상태가 달라짐!
```

### 해결 방안
**시간 간격 5분 조정:**
```
매일      00:00 - 챌린지 만료 처리
월요일    00:05 - 챌린지 활성화 (5분 간격)
월요일    00:10 - 영양제 생성 (5분 간격)
```

**파일:** `src/challenge/challenge-scheduler.service.ts`

```typescript
// Before
@Cron('0 0 * * 1')  // 00:00
async handleChallengeActivation()

@Cron('0 1 * * 1')  // 00:01
async handleWeeklySupplementCreation()

// After
@Cron('0 5 * * 1')  // 00:05 (5분 간격)
async handleChallengeActivation()

@Cron('0 10 * * 1')  // 00:10 (5분 간격)
async handleWeeklySupplementCreation()
```

```typescript
    await this.expireChallenge(challenge.id, challenge.userId);
```

## 3. 영양제 주간 생성 배치 로직 개선

### 문제점
초기 구현: CHALLENGER 상태 사용자만 대상
→ 챌린지 완료 후 NEWCOMER가 되면 영양제 데이터 생성 안 됨!

### 해결
**대상:** `user_challenges` 테이블에 데이터가 있는 모든 사용자
= 챌린지를 한 번이라도 시작했던 사람
= 현재 상태(NEWCOMER/CHALLENGER)와 무관

**파일:** `src/challenge/challenge-scheduler.service.ts`

```typescript
@Cron('0 10 * * 1')
async handleWeeklySupplementCreation() {
  // user_challenges에서 챌린지 경험자 조회 (중복 제거)
  const userChallenges = await this.prisma.userChallenge.findMany({
    select: {
      userId: true,
      user: { select: { id: true, email: true } }
    },
    distinct: ['userId']  // userId 기준 중복 제거
  });

  // 각 사용자마다 영양제 7일치 생성
  for (const { user } of userChallenges) {
    await this.createWeeklySupplementRecords(tx, user.id, now);
  }
}
```

**예시:**
- A 사용자: 1차 챌린지 완료 (NEWCOMER) → 영양제 계속 생성 ✅
- B 사용자: 2차 챌린지 진행 중 (CHALLENGER) → 영양제 계속 생성 ✅
- C 사용자: 3차 챌린지 시작 예정 (NEWCOMER) → 영양제 계속 생성 ✅

## 4. Kubernetes CronJob으로 멀티 팟 중복 실행 방지

### 문제점
쿠버네티스 팟이 여러 개(예: 3개) 있을 때:
- NestJS `@Cron` 데코레이터는 모든 팟에서 실행됨
- 영양제 7일치가 3배로 중복 생성됨!
- 챌린지 활성화도 3번 시도됨!

### 해결 방안
**Kubernetes CronJob 사용**
- 쿠버네티스가 단 1개의 Job만 실행 보장
- `concurrencyPolicy: Forbid`로 동시 실행도 방지

### 구현

#### 4.1. Kubernetes CronJob YAML 파일 생성

**파일 1:** `infra-gcp/k8s/cronjob-expire-challenges.yaml`
```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: expire-challenges
  namespace: biocom-api
spec:
  # KST 00:00 = UTC 15:00 (전날)
  schedule: "0 15 * * *"

  # 동시 실행 방지
  concurrencyPolicy: Forbid

  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: expire-challenges
            image: asia-northeast3-docker.pkg.dev/api-dev-biocom/biocom-api/biocom-api:latest
            command:
            - node
            - dist/main.js
            - --run-scheduler
            - expire-challenges
```

**파일 2:** `infra-gcp/k8s/cronjob-activate-challenges.yaml`
```yaml
# KST 00:05 월요일 = UTC 15:05 일요일
schedule: "5 15 * * 0"
command: [node, dist/main.js, --run-scheduler, activate-challenges]
```

**파일 3:** `infra-gcp/k8s/cronjob-create-supplements.yaml`
```yaml
# KST 00:10 월요일 = UTC 15:10 일요일
schedule: "10 15 * * 0"
command: [node, dist/main.js, --run-scheduler, create-weekly-supplements]
```

**중요 포인트:**
- KST → UTC 변환: KST는 UTC+9이므로 00:00 KST = 15:00 UTC (전날)
- 월요일: Cron에서 일요일=0, 월요일=1이므로 월요일 00:05 = 일요일 15:05 UTC
- `concurrencyPolicy: Forbid`: 이전 작업이 끝나지 않으면 새 작업 시작 안 함

#### 4.2. NestJS main.ts에 CLI 스케줄러 실행 모드 추가

**파일:** `src/main.ts`

```typescript
/**
 * 스케줄러 단독 실행 함수
 * Kubernetes CronJob에서 특정 배치만 실행할 때 사용
 */
async function runScheduler(schedulerName: string) {
  const logger = new Logger('Scheduler');
  logger.log(`🕐 스케줄러 단독 실행 모드: ${schedulerName}`);

  // ApplicationContext만 생성 (웹 서버 없이 배치만 실행)
  const app = await NestFactory.createApplicationContext(AppModule);

  try {
    const { ChallengeSchedulerService } = await import('./challenge/challenge-scheduler.service');
    const schedulerService = app.get(ChallengeSchedulerService);

    switch (schedulerName) {
      case 'expire-challenges':
        await schedulerService.handleChallengeExpiration();
        break;
      case 'activate-challenges':
        await schedulerService.handleChallengeActivation();
        break;
      case 'create-weekly-supplements':
        await schedulerService.handleWeeklySupplementCreation();
        break;
      default:
        logger.error(`알 수 없는 스케줄러: ${schedulerName}`);
        process.exit(1);
    }

    logger.log(`✅ 스케줄러 실행 완료`);
    await app.close();
    process.exit(0);
  } catch (error) {
    logger.error(`❌ 스케줄러 실행 실패`, error);
    await app.close();
    process.exit(1);
  }
}

// CLI 인자 확인 및 실행 모드 결정
const args = process.argv;
const runSchedulerIndex = args.indexOf('--run-scheduler');

if (runSchedulerIndex !== -1 && args[runSchedulerIndex + 1]) {
  // 스케줄러 단독 실행 모드
  runScheduler(args[runSchedulerIndex + 1]);
} else {
  // 일반 웹 서버 모드
  bootstrap();
}
```

**사용법:**
```bash
# 로컬 테스트
node dist/main.js --run-scheduler expire-challenges
node dist/main.js --run-scheduler activate-challenges
node dist/main.js --run-scheduler create-weekly-supplements

# Kubernetes CronJob에서 자동 실행
```

### 5.2. 경쟁 상태 방지

**시나리오 1: 월요일 자정**
```
00:00:00 - 만료 배치 시작
00:00:30 - 만료 배치 완료
00:05:00 - 활성화 배치 시작 (5분 간격으로 안전)
00:05:30 - 활성화 배치 완료
00:10:00 - 영양제 배치 시작 (5분 간격으로 안전)
```

**시나리오 2: 만료 배치가 오래 걸리는 경우**
```
00:00:00 - 만료 배치 시작
00:06:00 - 만료 배치 아직 진행 중...
00:05:00 - 활성화 배치 시작 시도
         → concurrencyPolicy: Forbid로 대기 또는 스킵
```

### 5.3. 멀티 팟 중복 실행 방지

**Before (문제):**
```
Pod 1: @Cron 실행 → 영양제 21건 생성
Pod 2: @Cron 실행 → 영양제 21건 생성 (중복!)
Pod 3: @Cron 실행 → 영양제 21건 생성 (중복!)
결과: 63건 생성 (3배)
```

**After (해결):**
```
Kubernetes CronJob: 1개 Pod만 실행 → 영양제 21건 생성
Pod 1, 2, 3: 일반 웹 서버로만 동작
결과: 21건 생성 (정확!)
```

## 6. DB 트랜잭션 격리 분석

### 경쟁 상태 발생 가능 지점

**만료 배치와 활성화 배치가 같은 사용자 처리 시:**
```typescript
// 만료 배치 (00:00)
UPDATE user_challenges SET status='EXPIRED' WHERE id=1  // 챌린지 A
UPDATE users SET status='NEWCOMER' WHERE id=100

// 활성화 배치 (00:05 - 동시 실행될 경우)
UPDATE user_challenges SET status='ACTIVE' WHERE id=2   // 챌린지 B
UPDATE users SET status='CHALLENGER' WHERE id=100

// 결과: 실행 순서에 따라 최종 상태가 달라짐!
```

### 자연스러운 격리

**대부분의 경우 충돌 없음:**
```typescript
// 만료 배치: WHERE status='ACTIVE' AND endDate < today
// 활성화 배치: WHERE status='PENDING' AND startDate = today
// → 다른 status 조건으로 같은 레코드를 절대 건드리지 않음!

// 영양제 배치: user_challenges는 조회만 (INSERT 없음)
// → 읽기 전용이라 충돌 없음!
```

**5분 간격으로 완전히 해결:**
- 만료 배치 완료 후 5분 뒤 활성화 배치 시작
- 활성화 배치 완료 후 5분 뒤 영양제 배치 시작
- 순차 실행 보장

## 8. 주의사항

### 8.1. 시간대 (Timezone)
- **Cron 표현식은 UTC 기준**
- KST 00:00 = UTC 15:00 (전날)
- 월요일 00:05 KST = 일요일 15:05 UTC

### 8.2. Docker 이미지
- CronJob은 최신 이미지를 사용해야 함
- 배포 시 deployment.yaml과 cronjob.yaml 모두 이미지 태그 업데이트 필요

### 8.3. 환경변수
- CronJob Pod는 ConfigMap에서 환경변수 로드
- DB 연결 정보, API 키 등 필요

### 8.4. 리소스 제한
```yaml
resources:
  requests:
    memory: "512Mi"
    cpu: "250m"
  limits:
    memory: "1Gi"
    cpu: "500m"
```

## 💡 핵심 인사이트

1. **경쟁 상태는 시간 간격으로 간단하게 해결**
   - 복잡한 락 메커니즘보다 5분 간격이 더 안전하고 단순

2. **Kubernetes CronJob의 강력함**
   - 멀티 팟 환경에서 단 1개만 실행 보장
   - `concurrencyPolicy: Forbid`로 동시 실행 방지
   - 애플리케이션 코드 수정 없이 인프라 레벨에서 해결

3. **CLI 모드의 유용성**
   - 웹 서버와 배치를 같은 코드베이스로 관리
   - 환경변수, 의존성 모두 공유
   - 테스트와 디버깅이 쉬움

4. **배치는 멱등성(Idempotency)이 중요**
   - 같은 배치를 여러 번 실행해도 결과가 같아야 함
   - 예: 영양제 생성 시 중복 체크 필요

## 9. 영양제 API 개발

### 9.1. 영양제 루틴 조회 API

**Endpoint:** `GET /api/tracking/records/supplements/routine`

**파일:** `src/tracking/controllers/records.controller.ts`, `src/tracking/services/records.service.ts`

**기능:**
- 사용자의 맞춤 영양제 루틴 목록 조회
- 설문조사 결과로 할당된 동물 타입 기반 영양제 + 사용자가 추가한 영양제
- 당일 섭취 기록(morning/afternoon/evening) 포함

**응답 DTO:** `src/tracking/dto/supplement-routine-response.dto.ts`
```typescript
export class SupplementRoutineResponseDto {
  routineId: number;           // 루틴 ID
  productId: number;           // 상품 ID
  productName: string;         // 영양제명
  productImage: string | null; // 영양제 이미지 URL
  dosage: DosageDto;          // 복용 정보 (frequency, quantity, unit)
  isDefault: boolean;          // 기본 영양제 여부
  displayOrder: number;        // 노출 순서
  morning: boolean;            // 아침 섭취 여부 (당일 기록)
  afternoon: boolean;          // 점심 섭취 여부 (당일 기록)
  evening: boolean;            // 저녁 섭취 여부 (당일 기록)
}
```

**주요 로직:**
1. `user_supplement_routine` 테이블에서 사용자의 루틴 조회 (isActive=true)
2. `products` 테이블 조인하여 영양제 정보 가져오기
3. `product_info` JSON 컬럼에서 복용 정보 추출 (frequency_per_day, quantity_per_dose, unit)
4. `product_images` 테이블에서 MAIN 이미지 가져오기
5. 당일 `user_records`에서 섭취 기록 조회 (recordType='SUPPLEMENT', date=오늘)
6. Map으로 productId별 섭취 상태 매핑
7. 루틴 정보 + 섭취 상태 병합하여 반환

**테스트:**
```bash
curl -X GET 'http://localhost:10804/api/tracking/records/supplements/routine' \
  -H 'Authorization: Bearer {token}'
```

### 9.2. 영양제 섭취 기록 저장 API

**Endpoint:** `POST /api/tracking/records/supplements/intake`

**파일:** `src/tracking/controllers/records.controller.ts`, `src/tracking/services/records.service.ts`

**기능:**
- 여러 영양제의 아침/점심/저녁 섭취 여부를 한 번에 저장
- 당일 최초 기록 시 사진 업로드 필수
- 당일 최초 기록 시 포인트 100점 지급

**요청 DTO:** `src/tracking/dto/supplement-intake.dto.ts`
```typescript
export class SaveSupplementIntakeDto {
  imageUrl?: string;  // 영양제 사진 URL (당일 최초 기록시 필수)
  data: SupplementIntakeItemDto[];  // 영양제 섭취 데이터 배열
}

export class SupplementIntakeItemDto {
  productId: number;   // 영양제 상품 ID
  morning: boolean;    // 아침 섭취 여부
  afternoon: boolean;  // 점심 섭취 여부
  evening: boolean;    // 저녁 섭취 여부
}
```

**주요 로직:**
1. KST 기준 당일 날짜 가져오기 (`getKoreanToday()`)
2. 당일 영양제 기록 중 imageUrl이 있는지 조회
3. imageUrl 없고, 기존 기록에도 사진이 없으면 400 오류 반환
4. RequestBody의 배열만큼 루프 돌면서 각 레코드 업데이트
   - `user_records` 테이블에서 기존 레코드 찾기 (userId, recordType='SUPPLEMENT', date=오늘, metadata.productId)
   - metadata 업데이트: {productId, morning, afternoon, evening, imageUrl(있으면)}
5. 당일 최초 기록이면 포인트 100점 지급 (`pointService.addPoints()`)

**검증 규칙:**
- 당일 최초 기록 시 imageUrl 필수
- imageUrl이 있으면 기존 레코드의 imageUrl도 함께 업데이트

**테스트:**
```bash
curl -X POST 'http://localhost:10804/api/tracking/records/supplements/intake' \
  -H 'Authorization: Bearer {token}' \
  -H 'Content-Type: application/json' \
  -d '{
    "imageUrl": "https://image.example.com/12345.png",
    "data": [
      {"productId": 4, "morning": true, "afternoon": false, "evening": true},
      {"productId": 5, "morning": false, "afternoon": true, "evening": false}
    ]
  }'
```
